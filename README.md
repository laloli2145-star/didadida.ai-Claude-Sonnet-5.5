### Judge the Deliverable

Generating code is only part of a development task. A useful result also needs to fit the existing project, preserve expected behavior, and be understandable to the person reviewing it.

Start with bounded tasks:

- Implement a specific feature.
- Investigate and fix a bug.
- Add relevant tests.
- Refactor a small module.
- Explain a change clearly.

The useful comparison is how much work remains afterward—not how impressive the first response looks.

### Frontend Work Needs More Than a Good Screenshot

A page needs working controls, readable typography, responsive layouts, and sensible error handling.

Give the model requirements you can check. For example:

> Build a product landing page with features, pricing, and an FAQ. Support desktop and mobile layouts. Give every button a defined action, avoid meaningless placeholder content, and check the interactions before finishing.

Clear requirements make it easier to evaluate whether the model genuinely reduced your workload.

### Try Writing and Information Tasks Too

Everyday AI work also includes:

- Turning meeting notes into action items.
- Rewriting technical explanations for users.
- Extracting decisions from long documents.
- Organizing product requirements.
- Editing drafts without changing the facts.

For actual slide decks, spreadsheets, or other files, the surrounding application also needs appropriate tools. Model capability alone does not provide a complete file-generation workflow.

### Measure the Cost of Finishing

Token price and task cost are different.

Fewer retries and less unnecessary output can reduce spending even when the unit price stays the same. A cheap request that repeatedly fails may be expensive in practice.

Check three things:

1. Did the result meet the requirements?
2. How long did the complete task take?
3. What did it cost, including retries?

Where supported, match reasoning settings to the task instead of automatically choosing the highest level.

### Give Different Models Different Jobs

A routine component change does not require the same approach as an open-ended architecture decision.

One workflow worth testing is to use Sonnet for well-defined work and consider a stronger model when a task requires difficult tradeoffs or remains unresolved.

Let your results determine the division of work.
